## Stock database: stored Instore read model (migration 070)

**Time:** 14:20 SAST

**Summary.** Added `migrations/070_instore_catalogue.sql` and applied it to the
stock Supabase project (`yiqsvwajozafvalwcero`). It creates the tables the main
portal now uses to serve Instore Products from an already-gated snapshot instead
of rebuilding the collection from `extended_range_items` and `website_stock` on
every customer request. No admin code changed and no existing table, function,
product, price, stock figure or Instore control was modified.

**What was created.**

- `public.instore_catalogue` — one row per eligible Instore product: its exact
  customer response payload, its browse category, its search tokens and its
  position in the default customer ordering.
- `public.instore_catalogue_staging` — a refresh stages its rows here and the
  swap happens in one statement, so a customer can never see a half-written
  collection.
- `public.instore_catalogue_state` — a single row holding the snapshot's
  freshness, product count, browse tiles, a fingerprint of the Instore
  image/listing controls it was built under, and the refresh lease.
- Functions `instore_catalogue_claim_refresh`, `instore_catalogue_release_refresh`,
  `instore_catalogue_stage`, `instore_catalogue_commit`.

All three tables have RLS enabled, are revoked from `anon` and `authenticated`,
and are granted only to `service_role`; the four functions are likewise
service-role-only. This is a cache of an eligibility decision, never a source of
truth — the portal ignores it when it is missing, stale, or built under
different Instore controls than the ones currently in force, and checkout still
verifies every line against the live index and the stock bridge.

**Effect on the admin app.** None required. `api/instore-image-controls.js` is
unchanged: the portal reads `instore_image_controls` and
`instore_listing_controls` live on every request, so hiding an Instore image or
listing from Product Manager still takes effect immediately.

**Verification.**

- Objects confirmed present: 3 tables, 4 functions, 1 state row.
- Functions exercised directly against the stock project: the refresh lease
  admits one claimer and refuses a second while held, refuses a claim while the
  snapshot is fresh, a staging count mismatch is rejected, a blank-SKU row is
  skipped, the commit swaps rows, stores tiles and clears the lease, and the
  stored-token prefix match (`LIKE '% wood%'`) works.
- Test rows were deleted and the state row reset; `instore_catalogue` and
  `instore_catalogue_staging` are empty pending the portal's first refresh.
- Expected first snapshot size, measured in SQL: 4,164 products (4,172 eligible,
  less 5 already on the main site and 3 hidden listings).

**Deployment status.** Migration applied to the production stock database.
Migration file committed and pushed to `claude/youthful-bohr-dhob72`. The
consuming code lives in ProtoMainSite (see that repository's journal entry for
today); no admin deployment is needed.

## Stock database: fix the Instore snapshot swap (migration 071)

**Time:** 17:25 SAST

**Summary.** Migration 070's snapshot swap could never run through the portal.
The Supabase REST role (`authenticator`) preloads `safeupdate`, which rejects an
UPDATE or DELETE with no WHERE clause — including statements inside a function —
so `delete from public.instore_catalogue;` failed with "DELETE requires a WHERE
clause" every time `instore_catalogue_commit` was called through the API.

`migrations/071_instore_catalogue_commit_safeupdate.sql` recreates the function
with `delete from public.instore_catalogue where sku is not null`. `sku` is the
primary key and therefore never null, so it matches every row and satisfies the
guard. Nothing else changes: the swap is still one transaction, an incomplete or
empty batch is still rejected, and an unchanged collection is still revalidated
without rewriting its rows. Applied to the stock project.

**How it was missed.** Migration 070 was verified by calling the functions
through this Supabase connection, which authenticates as `postgres` and has no
`safeupdate` preload, so the commit succeeded there. The guard only applies to
writes arriving through the REST API, which is how the portal calls it. Any
future migration that adds an unfiltered UPDATE or DELETE inside a function
needs checking against the REST path, not only a direct connection.

**Impact while it was broken.** No customer saw a wrong product and no data was
lost. The portal handles a failed snapshot write by logging it and releasing the
refresh lease, so it kept serving the correct products from its live read — it
simply never got any faster, because the snapshot could not be published. The
failure was recorded in `instore_catalogue_state.last_error`, which is how it
was found.

**Verification.**

- The replacement path — the one that failed, where a changed collection
  deletes the previous rows before inserting the new ones — was run end to end
  after the fix: two products committed, then a different single product
  committed over them, leaving only the new row.
- Every write statement in all four `instore_catalogue*` functions was listed
  from `pg_proc.prosrc` and confirmed to carry a WHERE clause: the snapshot
  delete by `sku is not null`, the staging cleanup by batch and age, and both
  state updates by the singleton `id`.
- The guard itself could not be loaded into this session (`access to library
  "safeupdate" is not allowed` for this role), so the fix is verified
  structurally plus functionally, not by reproducing the rejection here.
- Test rows removed and the state row reset: `instore_catalogue` and
  `instore_catalogue_staging` are empty, `last_error` is null, and the snapshot
  is unbuilt pending the portal's next request.

**Deployment status.** Applied to the production stock database. Because it is a
database function, it takes effect for every already-running deployment with no
redeploy.
