# 2026-09-24

## Stock database: stored Instore read model (migration 070)

**Time:** 14:20 SAST

**Summary.** Added `migrations/070_instore_catalogue.sql` and applied it to the
stock Supabase project (`yiqsvwajozafvalwcero`). It creates the tables the main
portal now uses to serve Instore Products from an already-gated snapshot instead
of rebuilding the collection from `extended_range_items` and `website_stock` on
every customer request. No admin code changed and no existing table, function,
product, price, stock figure or Instore control was modified.

**What was created.**

- `public.instore_catalogue` — one row per eligible Instore product: its exact
  customer response payload, its browse category, its search tokens and its
  position in the default customer ordering.
- `public.instore_catalogue_staging` — a refresh stages its rows here and the
  swap happens in one statement, so a customer can never see a half-written
  collection.
- `public.instore_catalogue_state` — a single row holding the snapshot's
  freshness, product count, browse tiles, a fingerprint of the Instore
  image/listing controls it was built under, and the refresh lease.
- Functions `instore_catalogue_claim_refresh`, `instore_catalogue_release_refresh`,
  `instore_catalogue_stage`, `instore_catalogue_commit`.

All three tables have RLS enabled, are revoked from `anon` and `authenticated`,
and are granted only to `service_role`; the four functions are likewise
service-role-only. This is a cache of an eligibility decision, never a source of
truth — the portal ignores it when it is missing, stale, or built under
different Instore controls than the ones currently in force, and checkout still
verifies every line against the live index and the stock bridge.

**Effect on the admin app.** None required. `api/instore-image-controls.js` is
unchanged: the portal reads `instore_image_controls` and
`instore_listing_controls` live on every request, so hiding an Instore image or
listing from Product Manager still takes effect immediately.

**Verification.**

- Objects confirmed present: 3 tables, 4 functions, 1 state row.
- Functions exercised directly against the stock project: the refresh lease
  admits one claimer and refuses a second while held, refuses a claim while the
  snapshot is fresh, a staging count mismatch is rejected, a blank-SKU row is
  skipped, the commit swaps rows, stores tiles and clears the lease, and the
  stored-token prefix match (`LIKE '% wood%'`) works.
- Test rows were deleted and the state row reset; `instore_catalogue` and
  `instore_catalogue_staging` are empty pending the portal's first refresh.
- Expected first snapshot size, measured in SQL: 4,164 products (4,172 eligible,
  less 5 already on the main site and 3 hidden listings).
