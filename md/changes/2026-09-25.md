# 2026-09-25

## Stock database: one-call Instore page read (migration 072)

**Time:** 00:30 SAST

**Summary.** Added `migrations/072_instore_catalogue_view.sql` and applied it to
the stock Supabase project (`yiqsvwajozafvalwcero`). It adds the read-only
function `instore_catalogue_view(p_category, p_from, p_limit)`, which returns the
snapshot's freshness and browse tiles, the current hidden image/listing control
SKUs, the matching total and the requested page of products in a single call.

The portal previously needed two sequential round trips for a landing or
category page: the snapshot state plus both control tables, then the page of
products. A customer with nothing cached now waits for one.

**What it does not do.** It does not decide whether the snapshot may be served.
It returns the current hidden-control SKUs alongside the fingerprint the
snapshot was built under, and the portal still derives and compares the
fingerprint itself, exactly as when it reads the control tables directly. Hiding
an Instore image or listing therefore still takes effect immediately. The portal
uses it only where it is the whole answer — not for a search, not for the
full-collection payload — and falls through to the reads it replaces on any
failure, including against a database that has not had 072 applied.

**Why this one is lower risk than 070.** It is read-only, so it is not exposed to
the `safeupdate` guard on the Supabase REST role that broke migration 070's
snapshot swap and needed 071 to fix.

**Files / systems affected.** `migrations/072_instore_catalogue_view.sql`. No
admin code changed. The consuming code is in ProtoMainSite (see that
repository's journal entry for today).

**Verification.** Exercised against production data before the portal was wired
to it: 60 products with a total of 4,280 and 13 tiles for the landing page; 0
products with a total of 50 for Bracelets page 2 (correctly an empty page past
the end, not a wrong total); the three real hidden listing SKUs returned; and its
first product confirmed to match the stored sort order. On the portal side its
output is asserted equal — products and total — to the two reads it replaces,
across seven request shapes.

**Deployment status.** Applied to the production stock database. Being a
read-only database function it takes effect with no redeploy; the portal change
that calls it is deployed separately from ProtoMainSite.
